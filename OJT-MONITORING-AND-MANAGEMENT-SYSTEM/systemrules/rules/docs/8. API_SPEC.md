# API and Backend Contract

## General Rules
- Protected operations require authentication.
- Authorization is enforced server-side and/or through approved database policies.
- Clients cannot grant themselves roles.
- Clients cannot approve their own registration.
- Clients cannot directly set credited internship hours.
- Errors must not be disguised as success.

## Approved Resource Areas
- Authentication: student registration, sign in/out, password reset.
- Registration approval: list pending, approve, reject.
- Companies/assignments: approved company management and assignments.
- Attendance: Time In, Time Out, offline sync, authorized retrieval, verification.
- Reports: upload, list, review/status according to role.
- Progress: retrieve and backend-controlled recalculation.
- Evaluations: create for assigned student, authorized retrieval.
- Notifications: list, read state, approved announcements/system events.
- Chat: list eligible counterparts and existing pair threads; atomically create a pair thread on first send; send immutable text messages; mark the current participant's thread read. Chat is available only to active Coordinators/Supervisors with an active department-linked placement.
- Administration: technical account status operations.

## Response Categories
Success, validation failure, unauthenticated, unauthorized, not found, conflict, server failure, synchronization rejection.

## Offline Sync
Pending attendance must include approved event metadata but cannot dictate final server authorization or credited status. Duplicate/conflicting events must be safely rejected or resolved.

## Chat
Chat messages are limited to non-empty plain text of at most 4,000 characters. Realtime delivery is scoped by the same participant RLS used for reads. A chat notification contains a generic sender label and conversation link, never the message body.

## Files
Exact file types and size limits remain subject to institutional requirements and must not be invented as research findings.
