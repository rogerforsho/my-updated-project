ENGINEERING_STANDARDS.md
________________________________________
Purpose
This document defines the engineering standards that govern the development of the Cross-Platform OJT Monitoring and Management System.
Its purpose is to ensure that every implementation is:
•	correct
•	scalable
•	maintainable
•	secure
•	testable
•	consistent
•	production-ready
This document has higher priority than implementation decisions.
If implementation conflicts with this document, this document takes precedence unless officially updated.
________________________________________
Core Engineering Principles
Every implementation must follow these principles.
1. Single Source of Truth
The backend is the only authoritative source of data.
The frontend must never become the source of truth.
Mobile and Web only display data returned by the backend.
Business rules must never exist in multiple places.
Examples:
•	internship hour computation
•	attendance validation
•	approval logic
•	permission checking
•	verification status
•	report status
must exist in one backend implementation only.
________________________________________
2. Shared Business Logic
Business logic must never be duplicated.
If the same computation is required by:
•	Mobile
•	Web
•	Admin
•	Coordinator
it must be implemented once and reused.
Never copy the same logic across multiple files or platforms.
________________________________________
3. Backend Authority
The frontend is responsible only for:
•	collecting user input
•	displaying data
•	sending requests
•	displaying results
The backend is responsible for:
•	validation
•	authorization
•	permission checking
•	business rules
•	calculations
•	database updates
Clients must never decide business outcomes.
________________________________________
Scalability Standards
The system must support growth without redesigning its architecture.
Growth includes:
•	more students
•	more companies
•	more supervisors
•	more coordinators
•	more schools
•	larger databases
•	higher request volume
Every feature should be designed assuming future growth.
________________________________________
Configurability
Never hardcode business values.
Examples:
•	required internship hours
•	departments
•	programs
•	academic year
•	semester
•	attendance schedule
must be configurable whenever appropriate.
________________________________________
Pagination
Large datasets must not be loaded entirely.
Use pagination for:
•	attendance history
•	student lists
•	reports
•	companies
•	notifications
•	evaluations
Never assume datasets remain small.
________________________________________
Efficient Queries
Only retrieve required fields.
Avoid unnecessary database queries.
Prevent repeated queries inside loops.
Optimize database access before optimizing UI.
________________________________________
Database Indexing
Frequently searched fields should be indexed.
Examples include:
•	student number
•	email
•	attendance date
•	company
•	status
•	foreign keys
Indexes should support expected access patterns.
________________________________________
Maintainability Standards
The project should remain understandable after years of development.
________________________________________
Clean Architecture
Separate:
•	UI
•	business logic
•	services
•	repositories
•	database access
•	utilities
Avoid tightly coupled code.
________________________________________
Small Functions
Functions should perform one responsibility.
Avoid extremely large functions.
Favor readable code over clever code.
________________________________________
Naming
Use descriptive names.
Avoid abbreviations unless universally understood.
Names should clearly describe purpose.
________________________________________
Reusability
Do not duplicate components.
Do not duplicate utilities.
Do not duplicate services.
If reusable code already exists, use it.
________________________________________
Data Integrity Standards
The database must remain internally consistent.
________________________________________
Referential Integrity
Foreign keys must remain valid.
Do not leave orphaned records.
Relationships must accurately reflect the ERD.
________________________________________
No Duplicate Truth
Store information once whenever possible.
Avoid storing derived values unless justified.
Example:
Completed internship hours should be derived from valid attendance according to approved business rules.
________________________________________
Atomic Operations
Critical database updates should complete fully or not at all.
Avoid partially completed operations.
________________________________________
API Standards
Every API endpoint must follow this order:
1.	Authenticate
2.	Authorize
3.	Validate
4.	Execute business logic
5.	Update database
6.	Return response
Never bypass validation.
Never trust client input.
________________________________________
Security Standards
Security is mandatory.
________________________________________
Authentication
Every protected resource requires authentication.
________________________________________
Authorization
Every protected action requires permission verification.
Never trust:
•	frontend role
•	hidden fields
•	disabled buttons
•	client claims
Always verify permissions on the backend.
________________________________________
Secrets
Never expose:
•	service keys
•	database passwords
•	JWT secrets
•	environment secrets
Secrets must never be committed to version control.
________________________________________
Sensitive Files
Attendance selfies and protected documents must use secure storage.
Do not expose permanent public URLs for sensitive files unless explicitly approved.
________________________________________
Offline Standards
Offline support must never compromise data integrity.
Offline does not mean accepted.
Offline means:
Pending Synchronization.
Backend validation remains authoritative.
Conflicts must never be silently overwritten.
________________________________________
Error Handling Standards
Every feature must define behavior for:
•	success
•	validation failure
•	unauthorized access
•	forbidden access
•	missing data
•	expired QR
•	invalid QR
•	duplicate request
•	offline state
•	synchronization failure
•	server failure
•	timeout
Never implement only the successful path.
________________________________________
Logging Standards
Important actions should be traceable.
Examples:
•	registration approval
•	attendance verification
•	evaluation submission
•	assignment changes
•	report review
Logs should identify:
•	actor
•	action
•	timestamp
•	affected resource
________________________________________
UI Standards
The interface must not contain business logic.
The UI should:
•	collect input
•	display information
•	call backend services
•	present system status
Do not compute business results inside UI components.
________________________________________
Performance Standards
Avoid unnecessary rendering.
Avoid unnecessary network requests.
Avoid loading large datasets unnecessarily.
Prefer efficient data retrieval.
Optimize only after identifying bottlenecks.
________________________________________
Code Quality Standards
Code must be:
•	readable
•	modular
•	reusable
•	testable
•	maintainable
Avoid:
•	duplicated logic
•	dead code
•	commented production code
•	deeply nested logic
•	unnecessary complexity
________________________________________
Testing Standards
A feature is not complete until tested.
Each feature should be verified for:
•	normal operation
•	invalid input
•	permission enforcement
•	failure scenarios
•	offline behavior (if applicable)
•	synchronization behavior (if applicable)
Never claim a feature works without verification.
________________________________________
Documentation Standards
Every significant architectural decision should be documented.
Documentation must remain synchronized with implementation.
If implementation changes:
•	API
•	database
•	workflows
•	permissions
•	requirements
the corresponding documentation must be updated.
________________________________________
Change Management
Before implementing any feature, determine:
•	affected requirements
•	affected workflows
•	affected roles
•	affected database tables
•	affected APIs
•	affected permissions
•	affected UI screens
•	affected tests
Do not implement changes without understanding their impact.
________________________________________
AI Development Rules
Any AI assisting this project must follow these rules.
Before generating code, the AI must verify:
•	Does this feature exist in the PRD?
•	Does this follow the approved requirements?
•	Does this match the ERD?
•	Does this match the DFD?
•	Does this match the workflow?
•	Does this duplicate existing logic?
•	Is the backend the source of truth?
•	Does this introduce technical debt?
•	Does this affect scalability?
•	Does this affect security?
•	Does this affect permissions?
•	Does this require documentation updates?
If any answer is unknown, the AI must stop and request clarification.
________________________________________
Definition of Done
A feature is considered complete only when:
•	Requirements are implemented.
•	Business rules are correct.
•	Security requirements are satisfied.
•	Permissions are enforced.
•	Errors are handled.
•	Offline behavior is handled where applicable.
•	Documentation is updated.
•	Tests pass.
•	No duplicated logic exists.
•	The implementation follows this Engineering Standards document.
Completion is determined by correctness, not by the absence of compilation errors.

Cross-Platform Compatibility Standards
Purpose
The system shall provide a consistent, reliable, and functional user experience across all officially supported platforms while maintaining a single centralized backend.
Cross-platform compatibility shall not require separate business logic or duplicated system functionality.
________________________________________
Supported Platforms
Version 1.0 shall support the following platforms:
Mobile Application
•	Android (supported by the current Expo SDK)
•	iOS (supported by the current Expo SDK)
Web Application
The responsive web application shall support current stable versions of major modern browsers, including:
•	Google Chrome
•	Microsoft Edge
•	Mozilla Firefox
•	Safari
Legacy browsers shall not be considered within the scope of Version 1.0.
________________________________________
Responsive Design
The web application shall provide a responsive interface that adapts to different screen sizes without requiring separate implementations.
The system shall support:
•	Desktop
•	Laptop
•	Tablet
•	Mobile browser
Core functionality shall remain available regardless of screen size.
________________________________________
Consistent Business Logic
Business rules shall remain identical across all platforms.
Examples include:
•	attendance validation
•	internship hour computation
•	role permissions
•	report submission rules
•	evaluation rules
Business logic shall exist only in the backend.
Neither the web application nor the mobile application shall implement separate versions of business logic.
________________________________________
Shared Backend
All supported platforms shall communicate with the same centralized backend.
No platform shall maintain its own independent database or separate business rules.
The backend remains the Single Source of Truth.
________________________________________
User Experience Consistency
Although user interfaces may be optimized for different screen sizes, users shall experience consistent workflows across supported platforms.
Equivalent features shall behave consistently regardless of device.
________________________________________
Device Independence
The application shall not rely on device-specific behavior unless explicitly required by an approved feature.
Platform differences shall not alter business rules or stored data.
________________________________________
Offline Compatibility
Where offline functionality is officially supported, behavior shall remain consistent across supported mobile devices.
Data collected offline shall synchronize with the centralized backend once connectivity is restored.
The backend remains responsible for validating synchronized data.
________________________________________
Browser Compatibility
The responsive web application shall avoid browser-specific implementations whenever practical.
Standards-based web technologies shall be used to maximize compatibility across supported browsers.
________________________________________
Accessibility
Interfaces shall remain usable across varying screen resolutions and input methods.
Interactive components shall be responsive to touch input on mobile devices and pointer or keyboard input on desktop devices where applicable.
________________________________________
Future Compatibility
The system architecture shall allow future platform expansion without requiring major redesign of the backend or business logic.
Future platforms shall integrate through the existing centralized backend and follow the same engineering standards.
