# System overview

The OJT Monitoring and Management System supports student practicum administration: student onboarding, company placement, attendance and accomplishment reporting, supervisor review, academic oversight, and certificate completion. Its user-facing clients are an Expo mobile app for students and a Next.js web portal for staff; the portal's desktop wrapper reuses the same interface. The project also contains Supabase database migrations and policies that underpin the workflows. [Mobile navigation](../apps/mobile/src/navigation/StudentNavigator.tsx#L12-L89) · [Web navigation](../apps/web/src/components/layout/Sidebar.tsx#L36-L75) · [desktop app](../apps/desktop)

## Roles and access

The current user-facing roles are **OJT Student**, **Supervisor**, **OJT Coordinator**, and **Super Admin**. Code commonly stores these as `Student`, `Supervisor`, `Coordinator`, and `Admin`; the migration and accepted role decision document the current model. [Role decision](adr/0006-explicit-ojt-account-roles-and-review-ownership.md) · [role migration](../supabase/migrations/20261019211849_four_account_roles.sql#L1-L35)

| Role | Main implemented capabilities |
| --- | --- |
| **OJT Student** | Registers and, when active, uses the mobile app for attendance, progress, evaluations/results, reports, notifications, and account profile. Students can submit attendance and reports, but must use the mobile app rather than the staff portal. [Mobile auth navigation](../apps/mobile/src/navigation/AuthNavigator.tsx#L9-L18) · [student tabs](../apps/mobile/src/navigation/StudentNavigator.tsx#L12-L89) · [portal access guard](<../apps/web/app/(dashboard)/layout.tsx#L14-L22>) |
| **Supervisor** | Uses the web portal to work with assigned students, review attendance, approve or return daily reports with feedback, and enter midterm/final evaluations. [Supervisor navigation](../apps/web/src/components/layout/Sidebar.tsx#L65-L71) · [report decisions](<../apps/web/app/(dashboard)/supervisor/reports/page.tsx#L55-L96>) · [evaluations](<../apps/web/app/(dashboard)/supervisor/evaluations/page.tsx#L25-L40>) |
| **OJT Coordinator** | Uses the web portal for student registration review, placements and schedule proposals, company/branch and supervisor management, attendance exceptions, submissions, progress, appeals, departmental reports, messages, and notifications. A student-specific set of web navigation entries remains in the sidebar source, but that does not make the student portal routes accessible. ## End-to-end workflows

1. **Student onboarding and placement.** A student registers in the mobile app with identity/program details, privacy consent, and front/back student-ID images. The pending screen instructs the student to confirm email and wait for Coordinator review; coordinators can approve or reject registrations. Coordinators then manage company and branch records and assign a student to a company, branch, supervisor, and placement dates; the assignment screen also handles schedule proposals. [Registration form](../apps/mobile/src/screens/auth/RegisterScreen.tsx#L15-L98) · [pending guidance](../apps/mobile/src/screens/auth/PendingScreen.tsx) · [approval action](<../apps/web/app/(dashboard)/coordinator/approvals/page.tsx#L20-L90>) · [placement and proposals](<../apps/web/app/(dashboard)/coordinator/assignments/page.tsx#L14-L76>)
2. **Attendance and reporting.** Students record time-in/time-out in the mobile app, with selfie and location evidence. Attendance can be queued offline and synced later; synced records are marked pending verification rather than automatically approved. A Supervisor reviews attendance and daily accomplishment reports for assigned interns; report decisions require feedback. Coordinators can adjudicate attendance exceptions within their department grants, providing a reason that is audited. [Attendance capture and queue](../apps/mobile/src/services/attendance.ts#L89-L127) · [sync sets pending verification](../apps/mobile/src/lib/attendanceSyncWorkflow.ts#L59-L84) · [Supervisor reports](<../apps/web/app/(dashboard)/supervisor/reports/page.tsx#L55-L96>) · [Coordinator exceptions](<../apps/web/app/(dashboard)/coordinator/attendance/page.tsx#L70-L76>)
3. **Evaluation and completion.** Supervisors enter midterm/final evaluations. Coordinator-side clearance checks consider credited hours, an approved final report, and a passing final evaluation; the Coordinator records the final OJT grade. Certificate issuance and public verification are implemented as separate steps/routes. [Supervisor evaluation types](<../apps/web/app/(dashboard)/supervisor/evaluations/page.tsx#L25-L40>) · [clearance conditions](../apps/web/src/services/certificates.ts#L40-L152) · [final-grade and completion constraints](../supabase/migrations/20261021000100_coordinator_final_grade_and_completion_freeze.sql#L18-L59) · [public certificate verification](<../apps/web/app/verify-certificate/[code]/page.tsx>)
4. **Administration.** A Super Admin manages user access and can invite OJT Coordinators with one or more department scopes. The console also exposes announcement and audit-log actions. [Admin user actions](../apps/web/src/services/admin.ts#L86-L103) · [announcement and audit UI](<../apps/web/app/(dashboard)/admin/AdminClient.tsx#L43-L45>)

## Implementation boundaries and notes

- Role-specific sidebar entries describe the intended portal navigation; route layouts and service checks provide additional enforcement. For example, Coordinator routes require an active Coordinator account and Coordinator services validate department grants. [Coordinator route guard](<../apps/web/app/(dashboard)/coordinator/layout.tsx#L9-L21>) · [Coordinator service authorization](../apps/web/src/services/auth/account-review.ts#L7-L19)
- Mobile attendance records device-captured event times separately from server receipt times, and queued offline items are retained when they conflict with an existing server record. [Attendance sync workflow](../apps/mobile/src/lib/attendanceSyncWorkflow.ts#L38-L54) · [attendance migration](../supabase/migrations/20261020150000_attendance_server_receipt_times.sql)
- Internal compatibility role strings are not all user-facing roles. Earlier OJT Staff/Program Head terminology appears in older ADRs and migration history; use the four-role model above for current behavior. [Current role ADR](adr/0006-explicit-ojt-account-roles-and-review-ownership.md) · [historical ADR](adr/0005-four-account-roles.md)

This overview describes implemented routes and actions, not a guarantee that every workflow is deployed or enabled in a particular environment. Where a capability's availability depends on account grants, assignment, or account status, the implementation enforces that condition; it is not inferred as universal access.
