**Reviewed:** 2026-10-21. [free-for.dev](https://free-for.dev/) is a discovery list; the limits below come from each provider's current documentation. The repo has a Next.js web portal, Expo Android app, Electron wrapper, Supabase backend, Resend email queue, Sentry web instrumentation, GitHub Actions, and Leaflet maps using OSM public tiles and Nominatim. The [architecture](../../systemrules/rules/docs/11.%20ARCHITECTURE.md) and [pre-launch audit](../../PRE-LAUNCH-AUDIT-2026-10-11.md) identify monitoring, backup restore, and real-device testing as unfinished.

## For the production recovery gate

The [free-for.dev list](https://github.com/ripienaar/free-for-dev) helps find an **off-site destination**, not a service that automatically captures a complete Supabase project. For the [reset gate](../operations/production-data-reset.md), the useful free path is:

1. **Export the database with Supabase's tools.** Supabase does not provide automatic daily backups on Free and recommends regular `supabase db dump` exports. Its [CLI backup/restore guide](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) uses separate roles, schema, and data dumps, then a manual restore into a newly created project. Follow its additional steps for migration history and any modified Auth/Storage schemas. A manual restore needs separate handling of the encryption root key if Vault or encrypted columns are used. [Database backups](https://supabase.com/docs/guides/platform/backups), [CLI backup/restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).
2. **Export Storage files separately.** A database dump includes Storage metadata, not file bytes. Supabase documents bulk download with its CLI or an S3-compatible client such as rclone. Record every bucket/path, count and checksums, then restore sample files and open them in the rehearsal project. [Database backups](https://supabase.com/docs/guides/platform/backups), [download objects](https://supabase.com/docs/guides/storage/management/download-objects). Keep S3 access keys server-side because they bypass RLS. [S3 authentication](https://supabase.com/docs/guides/storage/s3/authentication).
3. **Store the recovery set off-site.** [Backblaze B2](https://github.com/ripienaar/free-for-dev#storage-and-media-processing) is a candidate, with the first 10 GB stored free; measure the actual dump plus file bytes before relying on that allowance. [B2 pricing](https://www.backblaze.com/cloud-storage/pricing). For student records, encrypt locally before upload and keep the decryption key separately; B2's server-side encryption leaves file names and other metadata unencrypted. [B2 encryption guidance](https://www.backblaze.com/docs/cloud-storage-server-side-encryption). B2 [Object Lock](https://www.backblaze.com/docs/cloud-storage-object-lock) can prevent deletion until a chosen date, but set a short reviewed retention because compliance-mode locks cannot be shortened.
4. **Rehearse in isolation.** Supabase's automated **Restore to a new project** requires a paid plan with physical backups; it is unavailable on Free. The free route is the manual CLI restore above into a separate project, subject to the Free plan's two-active-project, 500 MB database, and 1 GB Storage limits. [Clone feature](https://supabase.com/docs/guides/platform/clone-project), [Supabase pricing](https://supabase.com/pricing). A read-only check on 2026-10-21 found `CDM-OJT-Staging` is occupied: seven Auth users, seven application users, and its own migration history. It is unsuitable as an overwrite target without a separate review. Both production and staging currently occupy active project slots; if this organization is on Free, use an isolated local environment or arrange a separate paid project for rehearsal. This recommendation follows from the project inventory and platform limits; it has not been rehearsed here.

**Decision:** The recovery gate remains open until the database and Storage exports are readable, kept immutably, and a restore rehearsal passes. Neither free-for.dev nor B2 substitutes for those checks. The later local export and rehearsal are recorded in the [reset gate](../operations/production-data-reset.md); an independent protected copy remains outstanding.

## Suggested order

1. Set up external checks against deployed `/health` and `/ready`; the former returns a simple response while the latter probes selected backend dependencies.
2. Build and test the Android APK on a physical phone; use Appetize only for additional UI review.
3. Rehearse database **and** Storage-object backup restoration; measure whether the free object-storage allowance covers the actual data.
4. Load-check the map search and tile traffic, then decide whether Geoapify is needed. Public Nominatim and OSM tiles have usage policies, not guaranteed capacity.

No accounts, plans, or integrations were changed by this research. Free limits are account-level and may change; check the provider dashboard before committing production traffic or sensitive backup data.
