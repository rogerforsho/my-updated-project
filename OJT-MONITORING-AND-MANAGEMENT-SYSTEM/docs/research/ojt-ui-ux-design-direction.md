# UI/UX direction for the OJT monitoring system

**Reviewed:** 2026-10-20  
**Question:** What interface direction fits the approved OJT roles and workflows?

## Recommendation

Use a **task-first academic operations interface**: a focused student mobile app for attendance and submissions, and a queue-and-detail workspace for staff review. Borrow interaction patterns, not another product's branding or component library. The project's [requirements](../../systemrules/rules/docs/4.%20REQUIREMENTS.md), [UI inventory](../../systemrules/rules/docs/10.%20UI_UX_GUIDELINES.md), and [ADR 0006](../adr/0006-explicit-ojt-account-roles-and-review-ownership.md) define four roles with different clients and access. The existing web already has a role-based sidebar, reusable UI components, and a green/sand theme (`apps/web/src/components/layout/Sidebar.tsx`, `apps/web/src/components/ui/`, `apps/web/app/globals.css`); the mobile app already has student tabs and an attendance capture flow (`apps/mobile/src/navigation/StudentNavigator.tsx`, `apps/mobile/src/screens/attendance/AttendanceScreen.tsx`). Refine those structures instead of starting a new visual system.

| Role | Recommended first view and interaction |
| --- | --- |
| Student, mobile | Show **credited hours, remaining hours, today's attendance state, next required task, and recent feedback**. Keep one prominent Time In or Time Out action according to the current session; show requirements and reports as short task rows with a text status and next action. The current navigator has six tabs; test grouping these into three to five peer destinations, with deeper steps inside them, as Android recommends. Use a task-list pattern for pre-deployment documents only if students can complete them in either order; GOV.UK advises against this pattern for mandatory ordered steps. [Android layout and navigation patterns](https://developer.android.com/design/ui/mobile/guides/layout-and-content/layout-and-nav-patterns); [GOV.UK task list](https://design-system.service.gov.uk/components/task-list/). |
| Supervisor, web/desktop | Start with assigned students and **attendance and daily-report review queues**. Show actionable count, age, and exception reason; open a selected item into evidence and a clear verify/return decision. Keep evaluations separate from routine attendance. This is an inference from the ownership rules in [ADR 0006](../adr/0006-explicit-ojt-account-roles-and-review-ownership.md) and Carbon's guidance for searchable, sortable data tables and row/batch actions. [Carbon data tables](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines). |
| Coordinator, web/desktop | Start with department scope, registration/gateway/placement queues, exceptions, then monitoring. Each queue should expose its current filters and show the approval reason/remarks in the detail view. The department grant must remain visible so staff understand which records they are reviewing. This layout follows the approved role scope in [ADR 0006](../adr/0006-explicit-ojt-account-roles-and-review-ownership.md); Carbon places search, filters, and actions in the table toolbar. [Carbon data tables](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines). |
| Super Admin, web/desktop | Present only account access, system configuration, and security audit metadata, behind MFA. Do not use a combined academic dashboard; the restriction comes from [FR-ADMIN-001/002](../../systemrules/rules/docs/4.%20REQUIREMENTS.md) and [ADR 0006](../adr/0006-explicit-ojt-account-roles-and-review-ownership.md). |

## Interaction details

- **Status language:** Use a short, consistent state vocabulary drawn from the real workflow: for example, `Needs action`, `Pending review`, `Approved`, `Returned`, and `Finalized`. Show the state in text, plus its date and reviewer remarks where relevant. Keep `Submitted` distinct from `Approved`, and `Pending sync` distinct from `Credited`. GOV.UK recommends short sentence-case task statuses and as few variants as users need; Carbon says color alone cannot carry status. [GOV.UK complete multiple tasks](https://design-system.service.gov.uk/patterns/complete-multiple-tasks/); [Carbon status indicators](https://www.carbondesignsystem.com/building-blocks/core/patterns/status-indicators); [FR-REP-002 and FR-SELFIE-005](../../systemrules/rules/docs/4.%20REQUIREMENTS.md).
- **Review queues:** Default to items requiring a decision. Put search/filter/sort above the list; show student, date, status, exception cue, and next action. A row opens a detail view with the evidence and decision controls. Allow batch verification only for the approved clean-attendance case, with explicit selection count and a visible action bar. Carbon documents this table and batch-action pattern. [Carbon data tables](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines); [FR-SELFIE-004](../../systemrules/rules/docs/4.%20REQUIREMENTS.md).
- **GPS and selfie capture:** Explain immediately before Time In/Out that the app uses a live front-camera selfie and one location sample as review evidence. Request permissions in the action's context; explain how to recover if denied or location is unavailable. Preview the captured evidence and show `Awaiting review` after submission. Do not imply continuous tracking, identity matching, or automatic GPS-based rejection. Android recommends in-context location permission requests and notes that users may grant only approximate location; the project's [FR-GPS-001/002 and FR-SELFIE-001/002](../../systemrules/rules/docs/4.%20REQUIREMENTS.md) set the actual product boundary. [Android location permission guidance](https://developer.android.com/develop/sensors-and-location/location/permissions/runtime).
- **Responsive staff views:** Keep full data tables where comparison matters on desktop. At narrow widths, reflow the surrounding page and show the same essential record fields in a stacked list/detail presentation; keep actions visible without hover. Verify at 320 CSS px and 400% zoom. Carbon advises persistent actions for touch; WCAG 2.2 requires reflow without losing content or function, with an exception for genuinely two-dimensional data tables. [Carbon data tables](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines); [WCAG 2.2, Reflow](https://www.w3.org/TR/WCAG22/#reflow).
- **Accessibility:** Aim for WCAG 2.2 AA on web: at least 4.5:1 normal text contrast, visible keyboard focus, accessible status announcements, labeled controls and errors, and pointer targets at least 24×24 CSS px or sufficient spacing. For the native mobile controls, use at least 48 dp touch targets. Test both light and dark palettes and text enlargement. [WCAG 2.2](https://www.w3.org/TR/WCAG22/); [Android accessibility](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility).

## Visual direction

Keep the existing **deep green `#092E1D` / `#0A3824`, warm off-white `#F4F6F2`, sand `#E4DBC4`** palette from `apps/web/app/globals.css` and the mobile attendance screen. Use green for navigation and primary actions, pale neutral surfaces for record-heavy screens, and restrained sand/gold for emphasis. Use typography, spacing, borders, and explicit labels to establish hierarchy; reserve attention colors for states that need action. Check every actual foreground/background pairing for contrast rather than assuming that a branded color passes. [WCAG 2.2, Contrast (Minimum)](https://www.w3.org/TR/WCAG22/#contrast-minimum); [Carbon status indicators](https://www.carbondesignsystem.com/building-blocks/core/patterns/status-indicators).

## Decision to resolve before designing attendance states

The repository conflicts on offline attendance: root `AGENTS.md` allows mobile offline logging and automatic sync; [FR-ATT-008](../../systemrules/rules/docs/4.%20REQUIREMENTS.md) requires an active connection and says offline attendance is unsupported; the [UI inventory](../../systemrules/rules/docs/10.%20UI_UX_GUIDELINES.md) asks for connectivity/sync state; and the mobile attendance screen contains an offline queue and sync flow. Resolve the authoritative rule before finalizing capture, pending-sync, error, and credited-hour screens. If offline capture is approved, never label locally queued evidence as verified or credited before human review, as [ADR 0006](../adr/0006-explicit-ojt-account-roles-and-review-ownership.md) requires.

**Scope:** This is a design recommendation from project documents and official platform/design-system guidance. It does not claim that the current screens conform or that user testing has validated the layout.

